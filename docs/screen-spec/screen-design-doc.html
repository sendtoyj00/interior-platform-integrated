1.2 화면 ID 체계 및 작성 원칙

  • 화면 ID는 SCR-{대분류코드}-{일련번호} 형식을 사용하며, 요구사항 정의서의 "관련 화면 ID" 컬럼과 1:1로 매핑된다 (추적성 체계는 부록 6.2 참조).
  • 본 문서는 그레이스케일(Grayscale) 와이어프레임 원칙을 따른다 — 컬러는 네비게이션/강조 버튼 등 최소한의 위계 표현에만 제한적으로 사용하고, 레이아웃·정보구조·UX 흐름 검증에 집중한다.
  • 화면 내 모든 상호작용 요소(버튼·입력필드·토글·탭·테이블 행 액션)에는 번호 배지(①②③…)를 부여하고, 각 화면의 디스크립션 표에서 NO / 구분(Happy Path·Edge Case) / UI 요소명 / 인터랙션 및 로직 정의 / 이동 화면·비고 / 매핑 요구사항ID 6개 컬럼으로 상세 기술한다.
  • 모든 액션 버튼은 아이콘 단독이 아닌 한글 동사형 라벨을 명확히 병기하여 가시성을 확보한다 (예: "가입하기", "견적서 발송", "승인", "반려", "재발송").

03 서비스 개요 및 정보 구조도 (IA & User Flow)

3.1 서비스 개요

서비스명: 인테리어 회사를 위한 중립형 B2B2C 업무 플랫폼
목적: 인테리어 업체가 고객관리부터 견적, 계약, 시공관리, 결제, 고객 알림까지 필요한 업무 기능을 선택하여 사용하고, 고객은 업체가 공유한 프로젝트에 참여해 공사 진행 정보를 확인할 수 있는 중립형 업무 플랫폼.

  • 업체: 필요한 업무 모듈만 선택하여 반복 업무를 줄인다.
  • 고객: 견적·계약·공정·결제·사진 등 자신의 공사 정보를 한곳에서 확인한다.
  • 플랫폼: 특정 업체에 종속되지 않고 여러 업체가 독립적으로 사용할 수 있는 환경을 제공한다.
  • 이해관계자(5개 역할): 인테리어 업체 관리자, 현장 담당자, 인테리어 고객, 플랫폼 관리자, 외부 알림 API(비인격 주체).

04 공통 정책 및 규칙 (Global Policy & System Rules)

개별 화면 설계서에서 반복 기술하지 않고, 전 화면에 공통으로 적용되는 디자인·인터랙션·데이터·예외처리 규칙을 정의한다. 5장의 각 화면은 아래 공통 정책을 전제로 화면별 차이점만 기술한다.

4.1 디자인 시스템 / 와이어프레임 톤앤매너

  • 그레이스케일 원칙: 모든 화면은 컬러를 배제한 그레이스케일 와이어프레임으로 작성한다. 컬러는 네비게이션 강조·Primary 버튼 등 최소한의 위계 표현에만 제한적으로 허용한다.
  • 공용 컴포넌트: 전 20화면은 공용 app/globals.css(그레이스케일 shadcn 테마)와 공용 components/ui/button.tsx를 사용해 버튼·타이포·여백 톤을 통일한다.
  • 디바이스 프리뷰 규격: 화면마다 DESKTOP(1920×1080, 브라우저 크롬 UI 포함, 0.5 스케일 미리보기)과 MOBILE(360×800, 기기 노치 UI 포함) 두 프레임을 동시에 제공한다 (components/frame/device-preview.tsx). 콘텐츠가 프레임 높이를 초과하는 경우 프레임 내부 스크롤(overflow-y auto)로 처리하며, 본 문서의 캡처 이미지는 버튼 가시성 확보를 위해 프레임을 콘텐츠 높이에 맞춰 임시로 확장 렌더링한 것이다(4.2 참조).
  • 번호 배지 규칙: 설명이 필요한 모든 UI 요소 옆에 ①②③… 번호 배지를 부여하고, 우측/하단 디스크립션 표의 NO 컬럼과 1:1 대응시킨다.
  • 화면 상단 메타 배지: 모든 화면은 상단에 SCR-ID 카테고리 REQ-ID 대상 역할 배지와 메뉴 경로(breadcrumb), 화면 명칭을 고정 노출한다 (components/frame/screen-page-chrome.tsx).

4.2 버튼 및 라벨 가시성 규칙

본 문서는 "모든 버튼 이름의 가시성"을 필수 요건으로 한다. 이를 위해 다음 규칙을 전 화면에 적용한다.
  • 모든 액션 버튼은 아이콘 단독 사용을 지양하고 한글 동사형 라벨을 명확히 병기한다 (예: "가입하기", "로그인", "견적서 발송", "승인", "반려", "재발송", "상세보기").
  • Primary 버튼은 검정 배경 + 흰색 텍스트(또는 그 반전)로 최대 명도 대비를 확보하고, 비활성(Disabled) 상태에서도 라벨 텍스트는 항상 유지한 채 배경만 회색조로 낮춘다.
  • 모바일 프레임처럼 세로 폭이 좁은 레이아웃에서 버튼이 프레임 하단에 가려지는 경우를 방지하기 위해, 프레임은 콘텐츠 높이에 맞춰 확장되거나(캡처 시) 스크롤 가능해야 한다(실서비스, 4.1 참조) — 실제로 본 설계서 작업 중 SCR-QUOTE-001 등 콘텐츠가 긴 화면에서 모바일 프레임 하단의 "견적서 발송" 버튼이 고정 800px 프레임에 가려지는 결함을 발견하여 overflow-hidden → overflow-y-auto로 수정하였다 (5장 해당 화면 각주 참조).

  • 금액: 천단위 콤마 + "원" 접미 표기 (예: 6,745,000원).
  • 날짜: YYYY-MM-DD 형식, 필요 시 시각까지 YYYY-MM-DD HH:mm 표기.
  • 상태값: 배지(badge) 형태로 표기하며 문의(신규/상담중/견적발송/종료), 계약(계약대기/체결/완료), 결제(대기/완료) 등 열거형 상태는 임의 자유 텍스트가 아닌 고정된 상태값 집합을 사용한다.
  • 필수 입력: 라벨 옆에 *를 표기하고, 필수 항목이 모두 유효하게 입력되기 전까지 제출성 버튼(가입하기/발송/저장 등)은 비활성 상태를 유지한다.

4.5 예외·오류 처리 공통 규칙

  • 유효성 오류(Validation): 필드 하단에 인라인 에러 메시지로 표시한다 (예: "이메일 또는 비밀번호가 올바르지 않습니다").
  • 시스템 오류: 네트워크 미연결·서버 500 오류 등은 공통 토스트 메시지로 노출한다.
  • 비인가 접근: 역할 권한이 없는 화면 진입 시 안내 문구와 함께 로그인 화면 또는 역할 홈으로 리다이렉트한다.
  • 보안 관련 요구사항은 프론트엔드 1차 검증 + 백엔드 최종 검증을 모두 충족해야 완료로 간주하며, 백엔드 검증이 누락된 경우 해당 요구사항은 미충족으로 처리한다 (요구사항 정의서 부록 A, 본 문서 부록 6.3에 재게재).

4.6 문서·추적성 관리 규칙

  • 화면ID(SCR-{대분류}-{일련번호})와 요구사항ID(REQ-{대분류}-{일련번호})는 항상 1:1 이상으로 교차 참조되며, 5장 각 화면의 "매핑 요구사항ID" 컬럼과 요구사항 정의서 4장의 "관련 화면 ID" 컬럼이 서로의 역참조가 된다 (추적성 매트릭스는 부록 6.2).
  • 문서 개정 시 버전과 변경이력 표(2장)를 함께 갱신한다(REQ-NFR-008).

05 상세 화면 설계 (Detailed Screen Specification)

전체 20개 화면을 요구사항 정의서 4장의 카테고리 순서(인증/계정관리 → 업체관리 → 고객문의관리 → 견적관리 → 계약관리 → 시공관리 → 결제관리 → 알림관리 → 대시보드 → 확장검토)대로 기술한다. 각 화면은 기본정보 → 초기 상태 → 와이어프레임(데스크톱/모바일 스크린샷) → 디스크립션(Happy Path/Edge Case 구분) → 예외 처리 및 정책 → 관련 화면 순서로 구성된다.

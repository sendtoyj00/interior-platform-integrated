## 1. 프로젝트 개요

### 1.1 서비스명

**인테리어 견적·시공관리 업무 플랫폼**

### 1.2 서비스 유형

인테리어 업체와 고객이 하나의 프로젝트를 기준으로 견적, 계약, 시공, 결제 및 공사 진행 정보를 관리·공유하는 **중립형 B2B2C 업무 플랫폼**이다.

### 1.3 문제 정의

인테리어 업무는 문의 접수부터 견적, 계약, 시공, 결제까지 여러 단계로 이루어지지만 업무 정보가 메신저, 문서, 스프레드시트 등에 분산될 수 있다.

이에 따라 다음과 같은 문제가 발생한다.

- 문의 및 고객 정보 관리가 분산됨
- 견적서와 수정 이력 관리가 어려움
- 공정 진행 상황을 고객에게 공유하기 어려움
- 결제 단계 및 상태 확인이 어려움
- 업체와 고객 사이의 정보 비대칭이 발생함

### 1.4 서비스 목적

인테리어 업체가 고객관리부터 견적, 계약, 시공관리, 결제, 고객 알림까지의 업무를 하나의 프로젝트 흐름으로 관리할 수 있도록 하고, 고객은 자신이 참여한 프로젝트의 진행 정보를 한곳에서 확인할 수 있도록 한다.

### 1.5 핵심 가치

| 대상          | 핵심 가치                                         |
| ------------- | ------------------------------------------------- |
| 업체 관리자   | 문의·견적·계약·프로젝트 업무를 통합 관리          |
| 현장 담당자   | 공정 및 시공 사진을 현장에서 관리                 |
| 고객          | 견적·계약·공정·결제 정보를 한곳에서 확인          |
| 플랫폼 관리자 | 업체 가입 및 권한을 관리하고 서비스 운영          |
| 플랫폼        | 특정 업체에 종속되지 않는 독립적인 업무 환경 제공 |

# 4. 요구사항 정의 및 관리 원칙

## 4.1 요구사항 분류

요구사항은 다음과 같이 관리한다.

- **기능 요구사항(FUNC):** 시스템이 무엇을 해야 하는지 정의
- **비기능 요구사항(NFR):** 시스템이 어떤 품질과 제약 조건을 만족해야 하는지 정의
- **보안 요구사항(SEC):** 인증, 인가, 개인정보, 데이터 보호 등에 대한 요구사항 정의

## 4.2 요구사항 ID 체계

요구사항 ID는 다음 형식을 사용한다.

```text
REQ-{대분류코드}-{일련번호}
```

예:

```text
REQ-AUTH-001
REQ-QUOTE-001
REQ-NFR-001
```

하위 기능은 다음 형식을 사용한다.

```text
FUNC-{대분류코드}-{요구사항일련번호}-{하위일련번호}
```

예:

```text
FUNC-AUTH-001-01
FUNC-AUTH-001-02
```

화면 ID는 다음 형식을 사용한다.

```text
SCR-{대분류코드}-{일련번호}
```

예:

```text
SCR-AUTH-001
SCR-QUOTE-001
```

### ID 관리 규칙

1. 요구사항 ID는 전체 문서에서 유일한 식별자로 사용한다.
2. 하나의 요구사항은 여러 하위 기능으로 분해할 수 있다.
3. 하위 기능은 FUNC ID로 구분한다.
4. 폐기된 ID는 재사용하지 않는다.
5. 요구사항 변경 시 기존 ID를 가능한 한 유지하고 변경이력을 기록한다.

## 4.3 우선순위

| 우선순위 | 의미                                         |
| -------- | -------------------------------------------- |
| Must     | MVP에 반드시 포함되어야 하는 기능            |
| Should   | 중요하지만 MVP 범위 및 일정에 따라 조정 가능 |
| Could    | 핵심 업무에는 필수적이지 않은 선택 기능      |

### 우선순위와 난이도는 별도로 관리한다.

- **우선순위:** 비즈니스 및 사용자에게 필요한 정도
- **난이도:** 설계·구현에 필요한 예상 복잡도

따라서 난이도가 높다고 우선순위가 높은 것은 아니다.

예:

| 요구사항                              | 우선순위 | 난이도 |
| ------------------------------------- | -------- | ------ |
| 비밀번호 재설정                       | Must     | 중     |
| 전자서명 연동                         | Could    | 상     |
| 산책이 아닌 본 서비스의 핵심 대시보드 | Should   | 중     |

---

## 4.4 범위 축소 기준

MVP 범위 축소 시 기본적으로 다음 순서로 판단한다.

1. Must 요구사항 유지
2. Should 요구사항 중 핵심 업무에 필요한 항목 유지
3. Could 요구사항 우선 보류
4. 외부 시스템 의존성이 높은 기능 보류
5. 학습 범위를 벗어나는 기능 보류
6. Must 요구사항을 제외하거나 보류할 경우 반드시 변경이력에 근거 기록

---

## 4.5 요구사항 상세 작성 기준

각 요구사항은 가능한 경우 다음 내용을 포함한다.

- 입력값
- 처리 방식
- 출력 결과
- 예외 조건
- 권한 조건
- 데이터 조건
- 제약사항

상세 설명은 단순한 기능명보다 **설계자가 동일한 요구사항을 재현할 수 있는 수준**으로 작성한다.

REQ → FUNC → SCR → API → DATA

# 15. 발표 핵심

10분 이내 발표에서는 전체 요구사항을 나열하지 않고 다음 내용을 중심으로 설명한다.

### 1. 문제 정의

인테리어 업무가 문의·견적·계약·시공·결제 단계별로 분산되는 문제

### 2. 핵심 서비스 흐름

```text
고객 문의
 → 견적
 → 견적 승인
 → 계약
 → 시공
 → 결제
 → 고객 확인
```

### 3. 요구사항 관리

- REQ/FUNC/SCR ID 체계
- Must/Should/Could 우선순위
- 난이도와 우선순위 분리
- 요구사항 변경이력 관리

### 4. 보안 설계

```text
Frontend
  ↓
1차 접근 제어

Backend
  ↓
최종 인증/인가 검증
```

### 5. 설계 산출물 연결

```text
REQ
 ↓
FUNC
 ↓
SCR
 ↓
API
 ↓
ERD
```

> **발표 핵심 메시지:**  
> "단순히 기능을 나열하는 것이 아니라, 요구사항을 ID로 관리하고 우선순위와 변경이력을 추적하여 화면·API·데이터 설계까지 연결하는 것을 목표로 했습니다."
